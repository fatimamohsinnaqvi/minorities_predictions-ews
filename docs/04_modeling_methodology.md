### Model 2 — PS-week forecaster (genuine early warning)

Score every police station BEFORE any incident has been reported, for the
upcoming 30 days. **This is the actual "early-warning" output.**

| Model | ROC AUC (test 2026) | Top-50 hits | Lift vs base rate |
|---|---|---|---|
| **Logistic Regression** | **0.7154** | 7 / 50 (Prec@50 = 0.14) | **18.5×** |
| Random Forest | 0.6386 | 0 / 50 | ineffective at top-K |

For PS-week forecasting **LR wins** (RF mis-calibrates on the very sparse
positive class — 1.35% base rate). LR meets the methodology's threshold
(≥ 0.65).

> **Validation caveat (read before citing these numbers).** The table
> above is a **single 2026 cutoff** (99 test positives) — fine as a
> headline, but noisy. A **rolling-origin re-test across six quarters**
> (2025Q1–2026Q2, expanding window, 30-day embargo against label leakage)
> gives the honest picture: **mean ROC AUC ≈ 0.70** (range 0.62–0.75),
> **mean lift ≈ 10× at top-10 / ≈ 7× at top-50**, and **Precision@20
> swinging from 0.20 down to 0.0** (two quarters caught nothing in the top
> 20). The "18.5×" is a best-case quarter, not the typical result. The raw
> LR scores are also **not calibrated probabilities** (mean ≈ 0.58 for a
> 0.75%-rate event); treat them as a risk ranking. Full method and results:
> [`08_temporal_validation.md`](08_temporal_validation.md). **For a paper,
> cite the rolling-origin numbers, not the single-cutoff ones.**

Per-PS forward scores for next 30 days are persisted in
`db_predictive_policing.minority_psweek_forward`, regenerated by
[`predict_psweek_forward.py`](../src/models/predict_psweek_forward.py).

**Top-15 PSes for next 30 days, Punjab-wide** (sample output):
Kahna, Chung, Nisthar Colony (all Lahore), Ferozewala (Sheikhupura),
Sadiqabad (Rawalpindi), Sadar Faisalabad. The Sialkot/Faisalabad picks
align with Research Design §4's historical clusters.

### Why two models

- **Per-case classifier** answers "is this incident, just reported,
  minority-targeted?" — useful for triage during the call-center
  workflow.
- **PS-week forecaster** answers "for the next 30 days, which PSes are
  most at risk for a minority-targeted incident?" — useful for proactive
  force-allocation planning.

Both run on the same upstream feature library; the difference is the
unit of analysis (per-incident vs per-PS-week) and the target (label of
a current case vs occurrence in a forward window).

All 4,110 cases have been scored by the per-case models and 656 PSes
have been forward-scored for the next 30 days.

### Model 3 — Prophet time-series (volume forecaster)

Complementary to the two classification models above. Predicts the
**total monthly volume** of minority-related cases for the next 3
months — useful for resource planning at the provincial level.

| Series | Validation MAPE | Next 3-month forecast (per month) |
|---|---|---|
| Punjab-wide | **9.54%** | 98 cases (80% CI: 86–110) |
| Lahore-only | 26.31% | 23 cases (80% CI: 16–29) |

**Important modeling decision:** the full case-volume series shows a
regime shift around October 2025 (case volume dropped from ~200/mo to
~90/mo and has been stable since). Rather than over-extrapolate this
shift with a linear trend, we train Prophet on the **post-shift window
only** with **flat growth** and **no yearly seasonality** (we have too
few cycles post-shift to learn it). Holiday regressors are kept (annual
events repeat).

The model essentially says: *"expect future monthly volume = current
level + adjustments for religious-holiday windows."*

Persisted in `data/processed/prophet_forecast_{punjab,lahore}.csv`.
Model card: [`outputs/reports/model_card_prophet.md`](../outputs/reports/model_card_prophet.md).

## Goal

Train and evaluate a small ladder of predictive models — Logistic Regression
baseline → Random Forest → optional XGBoost — to produce a per-row risk
score for minority-targeted incidents in Lahore. The output is both a
trained model artifact and a model-card documenting its performance,
fairness across communities, and known failure modes.

## Prediction task

**Unit:** an incident-context row from the feature table (Phase 3 output).
A "row" here is a place × time slice — for each PS-day or PS-week within
the training period, we ask: given the feature vector for this PS up to
time T, will an incident with `is_minority_targeted = TRUE` occur within
the next N days?

We will run the task at two horizons and report both:

| Horizon | N | Use case |
|---|---|---|
| 7-day | 7 | Operational deployment alert |
| 30-day | 30 | Policy / monthly briefing |

Positive class: any strict-label case in the (PS, T+N) window.
Negative class: all other PS-T cells.

## Models

| Model | Library | Why |
|---|---|---|
| **Logistic Regression** | `sklearn.linear_model` | Baseline; coefficients are directly interpretable; quick to train |
| **Random Forest** | `sklearn.ensemble` | Handles non-linear interactions and missing values natively; SHAP-friendly |
| **XGBoost** (optional) | `xgboost` | Best raw performance on tabular data; only adopted if RF results justify the extra opacity |

We will **stop at the first model that meets the success criteria below**,
to avoid over-engineering. The order is the order the Timeline PDF
prescribes.

## Train / test split

| Split | Period | Cases (approx) |
|---|---|---|
| Train | 2024-01 → 2025-12 | ~3,500 |
| Test | 2026-01 → 2026-06 | ~500 |

**Strict temporal split** — no future leaks into past. No random shuffle.
This matches operational reality (you predict the future from the past)
and guards against the prior-density features leaking labels.

## Metrics

We will report all of the following on the held-out test set:

| Metric | Why |
|---|---|
| Precision @ top-k (k=10, 20, 50) | Operationally, force allocation has finite budget — what fraction of the top-k flagged PS-weeks see an actual minority-targeted incident? |
| Recall @ top-k | What fraction of actual incidents fell in our top-k flags? |
| ROC AUC | Standard model-comparison metric, threshold-independent |
| PR AUC | Better than ROC under class imbalance (positive rate ≈ 5%) |
| F1 at chosen operating threshold | Single tuneable summary |
| Calibration plot | Are our risk scores well-calibrated probabilities? Critical for the dashboard's traffic-light bands. |
| Confusion matrix | At the chosen operating point, where do the errors fall? |

## Fairness / community-level evaluation

A critical addition not in the original timeline: every metric will be
**broken down by `minority_community`** on the test set:

| Community | Precision@20 | Recall@20 | ROC AUC |
|---|---|---|---|
| Christian | … | … | … |
| Ahmadi | … | … | … |
| Hindu | … | … | … |
| Sikh | … | … | … |
| Multiple / Unspecified | … | … | … |

If the model is systematically worse for any community (e.g., always
worse for Ahmadi cases due to small sample size), the policy brief will
say so explicitly. We will **not ship a model that performs much better
for the majority-tagged community than for a low-population minority** —
that would amount to building a system that protects some minorities
more than others.

## Success criteria

- LR baseline: ROC AUC ≥ 0.65 — meaningful lift over random.
- Random Forest: ROC AUC ≥ 0.75 and Precision@20 ≥ 0.30.
- The model also passes the fairness check (no community has AUC < 0.55).

If RF fails the fairness check but passes AUC, we **do not move to
XGBoost** — we go back to feature engineering or labeling, because more
model capacity will likely amplify the disparity.

## Decisions and trade-offs

- **No deep-learning models.** Sample size (~4,000 rows) doesn't justify
  the opacity. The supervisor and policymakers need to be able to ask
  "why did this PS get flagged?" — RF + SHAP can answer; a neural network
  cannot, at this scale.

- **Class imbalance handled with class weights, not oversampling.**
  Oversampling minority-targeted cases is tempting but inflates apparent
  performance via duplication. Class-weighted loss is honest.

- **No hyperparameter grid search in v1.** Default parameters with a
  single principled tweak (`class_weight='balanced'`) is enough for the
  baseline. Tuning happens only if v1 results justify it.

## Limitations

- Test set is only 6 months — limited statistical power for community
  breakdowns. Confidence intervals will be wide; we will report them.
- The "incident in next N days" label is sensitive to under-reporting.
  Communities that under-report will look like model false-positives.
- No way to estimate true incidents missed by both the model and the
  reporting system — selection bias is irreducible at this scale.
